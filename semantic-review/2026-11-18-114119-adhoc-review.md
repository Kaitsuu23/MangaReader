# MangaReader Flutter App — Runtime Bug Review

This codebase is a mature Flutter manga reader with multi-mode libraries, sync, and a background chapter tracker. The structure is solid but several confirmed bugs and a handful of likely ones are present across state management, async gaps, caching, and selection-mode data flows.

**Watch for:** A dead-statement in `_rebuildCachedData` corrupts the chapter read-state display for every user. The `_ensureTabController` mutation during `build()` will produce "setState during build" crashes on category changes. Source-keyed selection slugs are passed raw to `transferMultipleManga`, which will silently fail to transfer any items when multi-source keys are present.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The chapter cache in `MangaDetailsScreen` uses a length-only equality check to decide whether to recompute, so it misses the case where `readChapterSlugs` has changed but its count hasn't — leading to stale read-status rendering for every chapter in the list. The same function contains a dangling duplicate line that is a dead statement in Dart but signals that the boolean predicate was intended to be a compound condition, changing the semantics of `hasNewerChapters`.

The `FavoritesScreen` calls `_ensureTabController` from inside `build()` and from inside a `ListenableBuilder` child builder. When the tab count changes, `_ensureTabController` replaces the controller, which schedules a frame callback to dispose the old one — but the new `TabController` is not assigned to `_tabController` before the current build tree continues to reference the old object. This creates a window where `TabBar` and `TabBarView` are attached to two different controllers in the same frame.

History and Favorites both store selection keys as `source::slug` composites in `_selectedSlugs`, then pass the raw list to `showTransferMultipleMangaDialog(slugs: toTransfer)`. The dialog calls `LocalStorage.transferMultipleManga(slugs: slugs, ...)` which forwards each string directly to `transferManga(slug: ..., source: null)` with no source argument. A key like `softkomik::naruto` will be used verbatim as the slug, so the lookup in `_favoritesBox` and `_historyBox` will never match and the transfer silently does nothing.

The `FloatingNavbar` animation type dispatch in `_animTypeFor` is hardcoded to ordinal indices 0–3. If `MainScreen` ever reorders its tab list, or a consumer supplies a different-order `items` list, the wrong animation plays for every tab. This is a latent fragility, not a current crash.

<summary>Issues (13)</summary>

1. **Dead statement produces wrong `hasNewerChapters`** — `manga_details_screen.dart` line 183: the second copy of the condition is a dangling expression statement (no assignment). Dart evaluates it and discards the result. The intent was a multi-line `&&` chain, so `hasNewerChapters` is computed only from the first line of the predicate, potentially being `true` when it should be `false` or vice versa. Remove the duplicate line and confirm the full predicate is what was intended.

2. **Stale chapter read-status cache** — `_ensureCachedData` (line 216–221): the cache is skipped when `_cachedChronoChapters!.length == _details!.chapters.length && _cachedReadSlugs!.length == readChapterSlugs.length`. Two different sets of read slugs with the same cardinality will not trigger a rebuild. Chapters whose read status has just changed (e.g., user finishes a chapter) will continue to show stale indicators until the chapter count or read-slug count also changes. Use set equality or a generation counter instead.

3. **`_ensureTabController` mutates state during `build()`** — `favorites_screen.dart` lines 1421 and 1564: `_ensureTabController` is called directly from `build()` and from inside a `ListenableBuilder` builder. When the tab count changes, the method replaces `_tabController` with a new instance and defers the old one's disposal. Flutter will throw "setState() or markNeedsBuild() called during build" if any state mutation triggers a synchronous rebuild in the same frame. Move all controller replacement logic to `_onContentModeChanged` or `_refreshCategories`, never from within `build()`.

4. **Source-keyed selection slugs break `transferMultipleManga`** — `history_screen.dart` line 551 and `favorites_screen.dart` line 685: `_selectedSlugs` stores keys as `source::slug` (confirmed at history line 350: `_itemKey` returns `'$src::$slug'`; favorites line uses `'${item.source}::$slug'`). These composites are passed verbatim to `showTransferMultipleMangaDialog(slugs: toTransfer)`. Inside the dialog, each string goes straight to `transferManga(slug: rawSlug, source: null)`. The raw key `softkomik::my-manga` will be used as the slug with no source, the box lookup fails, and nothing is transferred. The slug must be split on `::` before passing to the dialog, or the dialog must accept `(slug, source)` pairs.

5. **`_selectedSlugs` key format inconsistency in `FavoritesScreen` delete path** — `favorites_screen.dart` lines 505–514: in `_confirmDeleteSelected`, `rawKey` is split on `::` to extract source and slug, correctly. But in `_showMoveCategoryDialog` (line 511), the same split logic is applied for the category move. When the slug itself contains `::` (possible with certain source IDs), `parts[0]` will be a fragment of the slug, not the source. Use `split('::', 2)` to limit to two parts.

6. **`ref.read(feedUpdateProvider.notifier).syncRunningStatus()` called after two `await`s without a `mounted` check** — `feed_screen.dart` line 34: `_checkPendingBackgroundUpdates` and `syncAllFeedItemsReadStatus` are both awaited before the `if (mounted)` guard that wraps `syncRunningStatus()`. However `_checkPendingBackgroundUpdates` itself does not check `mounted` before its own `setState()` at line 44. If the widget is removed from the tree between `addPostFrameCallback` firing and the two awaits completing, `setState` on the already-disposed widget will throw.  The fix: add a `mounted` guard at the top of `_checkPendingBackgroundUpdates`.

7. **`_handleMenuOption` uses `context` after `await` without `mounted` check in `mark_all_read` branch** — `feed_screen.dart` line 739–744: `await LocalStorage.markAllFeedItemsAsRead(...)` is called, then `ScaffoldMessenger.of(context)` is accessed inside `if (mounted)`. This is correct. However `_handleMenuOption` is not `async` — it uses an inline `async` block. Dart's `async` blocks inside a synchronous `switch` do not propagate exceptions back to the caller, so any exception inside the async block is silently swallowed. This is a confirmed silent-error risk.

8. **Double `RepaintBoundary` on every history card** — `history_screen.dart` lines 772 and 909: `_buildList` wraps each grid item in `RepaintBoundary` at line 772, and `_HistoryCard.build` wraps its own `InkWell` in another `RepaintBoundary` at line 909. The outer one (line 772) is redundant and wastes raster memory. Remove the outer wrapper.

9. **`_ensureCachedData` does not invalidate when `historyItem` changes** — `manga_details_screen.dart` lines 207–222: the cache-validity check ignores `historyItem` entirely. If the user opens the details screen, reads a chapter (which updates history), then returns to the details screen via the back-stack, `_cachedLastReadChronoIndex` and `_cachedIsCompleted` will not be recomputed because the chapter count and read-slug count are unchanged. The "Lanjutkan" / "Mulai Membaca" FAB label and the per-chapter read indicators will be stale. Add `historyItem?['updatedAt']` to the cache key or clear the cache on `initState` and `didChangeDependencies`.

10. **`listenContentMode()` returns a new `ValueNotifier` instance on every call** — `manga_details_screen.dart` lines 230 and 250: `LocalStorage.listenContentMode()` returns `contentModeNotifier`, which is a static singleton. Calling `addListener` and `removeListener` on the same singleton via two different call-site invocations is correct only if the same listener function reference is used for both. This is confirmed fine here, but the fact that `listenContentMode()` is called twice in both `initState` and `dispose` (duplicated lines) means the listener is registered twice and removed once, leaving a dangling listener after dispose. The grep shows each of lines 230 and 250 appears twice in the file — likely a copy-paste artifact. Remove the duplicate `addListener` / `removeListener` calls.

11. **`_onSearchOpenChanged` slide animation uses wrong curve on show** — `floating_navbar.dart` line 123: `_slideController.animateTo(0.0, curve: Curves.linearToEaseOut)` is used for the "show" animation, but the duration is set to `_slideShowDuration` (225ms). `Curves.linearToEaseOut` is not a standard Flutter curve and falls back silently to linear. The comment says "LinearOutSlowIn" should be used. Use `Curves.linearOutSlowIn` (the correct Flutter name). This causes the navbar to snap linearly back into view instead of easing in, which is a visible UX defect.

12. **`_showClearFeedDialog` captures stale `currentMode` after the dialog is dismissed** — `feed_screen.dart` line 757 + 775: `currentMode` is captured at the point `_showClearFeedDialog()` is called. If the user switches content mode while the dialog is open and then confirms, `clearFeed` will clear the previously-active mode's feed, not the now-active one. This is a likely user-visible bug if content mode switching is fast. Capture `currentMode` inside the `onPressed` callback.

13. **`transferMultipleManga` passes raw `source::slug` keys as slug-only arguments** — `local_storage.dart` lines 799–816: `transferMultipleManga` iterates the `slugs` iterable and passes each directly to `transferManga(slug: slug, source: null)`. When called from `HistoryScreen._transferSelected` or `FavoritesScreen._transferSelectedFavorites`, the slugs are `source::slug` composite keys. No source is extracted, so `getFavorite` and `getHistoryItem` perform a source-unscoped lookup with the full composite string as the slug, which will never match a stored entry. Count will be 0, nothing moves, and the UI shows success.

## Dead statement in `hasNewerChapters` computation

`manga_details_screen.dart`, `_rebuildCachedData`, lines 182–184:

```dart
final bool hasNewerChapters = !isCompleted &&
    lastReadChronoIndex >= 0 && lastReadChronoIndex < chronoChapters.length - 1;
    lastReadChronoIndex >= 0 && lastReadChronoIndex < chronoChapters.length - 1;
```

The second line is a standalone expression statement in Dart — it evaluates the boolean and throws it away. `hasNewerChapters` is computed from only the first predicate line. The correct intent is a single multi-line `&&` chain or the duplicate was left from a mid-edit state. Either way, the value is wrong whenever the two lines of conditions would produce a different result split versus joined.

The same duplication pattern appears at line 2028 in `build()` where `hasNewerChapters` is read from cache, but that's just the read side.

## Stale cache misses same-cardinality set changes

`manga_details_screen.dart`, `_ensureCachedData`, lines 216–221:

```dart
if (_cachedChronoChapters != null &&
    _cachedChronoChapters!.length == _details!.chapters.length &&
    _cachedReadSlugs != null &&
    _cachedReadSlugs!.length == readChapterSlugs.length) {
  return;
}
```

Consider: user reads chapter 5, which adds `slug5` to `readChapterSlugs` but also removes `slug4` from an earlier mark-unread. The count stays the same. The cache is not invalidated. Every chapter tile in the list continues to show the pre-read indicator state. This is confirmed by the fact that `readChapterSlugs` is derived fresh from `LocalStorage.getReadChapters` on every `build()` call, so the data is correct — but the cache guard throws it away.

## `_ensureTabController` called from `build()`

`favorites_screen.dart`, line 1421 (inside `build()`) and line 1564 (inside a `ListenableBuilder` builder):

`_ensureTabController` replaces `_tabController` with a new instance. This is state mutation. Calling it from within `build()` or any builder callback that runs synchronously during the build phase is unsafe in Flutter. The framework will raise an assertion failure on debug builds if the replacement triggers any downstream widget to `markNeedsBuild`. The deferred disposal via `addPostFrameCallback` does not eliminate this risk.

## Selection-key format mismatch in bulk transfer

`_itemKey` in `history_screen.dart` returns `'$src::$slug'` (line 350-ish). `selectKey` in `favorites_screen.dart` is `'${item.source}::$slug'`. Both are stored verbatim in `_selectedSlugs`. Both are passed directly to `showTransferMultipleMangaDialog(slugs: toTransfer)`.

`showTransferMultipleMangaDialog` at line 835 calls:

```dart
await LocalStorage.transferMultipleManga(
  slugs: slugs,
  fromModeId: currentFrom,
  toModeId: selectedTargetId,
  targetCategory: targetCategory,
);
```

`transferMultipleManga` calls `transferManga(slug: slug, source: null)` for each raw slug. `getFavorite('softkomik::my-manga', source: null, modeId: ...)` will iterate the box looking for a key containing `'softkomik::my-manga'` as the slug fragment — which does not exist since the box key format is `modeId::source::slug`. Transfer count returns 0, the success toast fires anyway.

The correct fix for `HistoryScreen._transferSelected` is to split the key before calling the dialog, or to pass `(slug, source)` pairs. For `FavoritesScreen._transferSelectedFavorites`, the same applies.

## Duplicate content-mode listener registration

`manga_details_screen.dart`, lines 230 and 250 each appear twice (duplicated by copy-paste):

```dart
LocalStorage.listenContentMode().addListener(_onContentModeChanged);  // ×2
...
LocalStorage.listenContentMode().removeListener(_onContentModeChanged);  // ×2 on dispose
```

`removeListener` on a `ValueNotifier` removes only one registration per call. After dispose, one listener copy remains. This leaks a reference to the disposed `_MangaDetailsScreenState` for the lifetime of the app, causing potential setState-on-unmounted-widget errors if `notifyContentModeChanged` fires after the screen is gone.

```dart
    builder: (ctx) => AlertDialog(
      onPressed: () async {
        Navigator.pop(ctx);
        await LocalStorage.clearFeed(modeId: currentMode.id); // used here, potentially stale
```

If the user opens the dialog, switches content mode from elsewhere (possible if another widget triggers `setActiveContentModeId`), then confirms deletion, the wrong mode's feed is cleared.

## Wrong slide-show curve in `FloatingNavbar`

`floating_navbar.dart`, `_onSearchOpenChanged`, line ~123:

```dart
_slideController.animateTo(0.0, curve: Curves.linearToEaseOut);
```

`Curves.linearToEaseOut` is not defined in Flutter's `Curves` class. This will throw a compile-time or analyzer error in strict mode, or silently resolve to the closest matching name. The correct name is `Curves.linearOutSlowIn`. As a result the hide animation uses the right curve (`Curves.fastOutSlowIn`) but the reveal animation uses the wrong one, making the navbar reappear abruptly.
